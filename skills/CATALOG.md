# Skills Catalog

> Generated by `scripts/skills catalog` from each skill's SKILL.md frontmatter.
> Do not hand-edit. `scripts/doctor` flags this file when it is stale.

| Skill | Use when |
|---|---|
| [adversarial-review](adversarial-review/SKILL.md) | Challenges a plan, design, decision, spec, or strategy before anyone commits to it: the strongest failure mode, the alternative not taken, the assumption doing the work, and one unhedged verdict. Use when asked to poke holes, argue the other side, find the weak point, or say why this will fail. Not for reviewing a code diff line by line, checking whether facts are true (research), or fixing the thing itself. |
| [artifact-quality](artifact-quality/SKILL.md) | Checks a finished document, PDF, deck, spreadsheet, or report before it goes to a reader: the rendered file opened and walked surface by surface, every chart honest to its data, every diagram true to the system, export defects caught. Use when finishing or auditing a static deliverable someone else will read. Not for drafts, not for the prose itself (written-voice), and not for live interfaces (implementation-verification). |
| [commit-and-pr](commit-and-pr/SKILL.md) | Shapes a commit or pull request another person will read later: read the diff first, one logical change per commit, a message that says why, no secrets, a branch off the shared default, and a PR body for a reviewer who has not seen the work. Use when committing, branching, or opening a PR. Not for scratch commits that will be squashed; a repository's own message format wins, the other checks still apply. |
| [context-mapping](context-mapping/SKILL.md) | Maps an unfamiliar codebase, service, or integration before anyone changes it: parts, owners, dependencies, boundaries, and unknowns, each tagged with how it was observed. Use when inheriting or taking over a system, before touching code whose neighbours you do not know, or when asked what depends on what. Not for entering a new role (org-entry), past decisions (research), or a one-line change whose neighbours do not matter. |
| [customer-discovery](customer-discovery/SKILL.md) | Plans, runs, and synthesizes customer interviews whose findings will be spent on a build or cut decision: a falsifiable assumption first, coverage of churned, closed-lost, and never-activated users, questions about past behavior only, saturation per segment, findings labeled observed, reported, or opinion. Use for validating a problem, a weekly interview habit, or a pile of interview notes. Not for usability tests, surveys, or desk research (research). |
| [decision-framing](decision-framing/SKILL.md) | Frames a decision that is expensive to reverse: the choice in one sentence, real options including do-nothing, trade-offs, one recommendation, its strongest objection, and a record a reader can audit later. Use for buy-or-build, vendor choice, X-or-Y arguments that will not settle, or "is it worth delaying to fix". Not for cheap reversible picks, and not for gathering the facts first (research). |
| [impact-measurement](impact-measurement/SKILL.md) | Turns your own work into evidence a skeptic can check: calibrate to the real rubric, reconstruct the period from records, write each claim as one evidence line with baseline, result, source, and an honest contribution verb, and include cancelled work. Use for a self-review, promotion packet, calibration submission, or contested stakeholder update. Not for product metrics (metric-design) or a routine status note. |
| [implementation-planning](implementation-planning/SKILL.md) | Use when asked to plan or sequence known work before building it: "write an implementation plan", "how would you build X", "plan this out", a change across several files or services. A task plan with the questions to decide first and a done-check on every task. Not for whether to build it (decision-framing), the spec (requirements-structuring), or a rollout (launch-readiness). |
| [implementation-verification](implementation-verification/SKILL.md) | Use when implementing a feature or fix, including a bare "fix it" or "make this work", refactoring, changing a schema or interface, or asked "is this done". A change plus evidence it works, from the project's own checks on the real surface. Not for review or research with no code change, throwaway scripts, or release readiness (launch-readiness). |
| [intake](intake/SKILL.md) | Turns a long, messy, or contradictory request into one brief: the primary outcome, constraints, decisions already made, open questions, and a parking lot for tangents. Use when a brain dump, forwarded thread, or pile of notes carries several asks at once and work is about to start. Not for a single clear ask, and not for a message that is thinking aloud with no ask yet. |
| [knowledge-base-curation](knowledge-base-curation/SKILL.md) | Proposes moves, renames, and archiving for a personal knowledge base of notes: stray and untitled files, notes in the wrong zone, active notes that have gone stale. Produces a short checklist a person ticks; nothing is moved by this skill. Use for a one-off or recurring tidy of a notes vault or notes folder. Not for files a mechanical rule already sorts, not for source code, and not for redesigning the vault's layout. |
| [launch-readiness](launch-readiness/SKILL.md) | Gates a customer-visible launch or rollout: a tier by blast radius and reversibility, cross-functional work scoped to the tier, an exposure sequence with a rehearsed kill switch, go/no-go criteria with one named decider, and a review against the metric registered before launch. Use for a launch, rollout, pricing or terms change, or GA step. Not for whether to build it (product-strategy) or the announcement (written-voice). |
| [metric-design](metric-design/SKILL.md) | Use when choosing a North Star, writing or fixing KRs, defining "active", or setting success criteria. A metric definition a team can be held to, with its counter-metric. Not for explaining why a number moved (root-cause-debugging) or evidencing your own work (impact-measurement). |
| [org-entry](org-entry/SKILL.md) | Plans the first months in a new leadership role, inherited team, or reorganized scope: classify the situation (start-up, turnaround, growth, realignment, sustaining), verify it against records, map where decisions are made, pick early wins that fit the type, and shape a 30/60/90 plan. Use for a new role, an inherited product or team, or a first-90-days ask. Not for reading a technical system (context-mapping). |
| [product-strategy](product-strategy/SKILL.md) | Use for where-to-play or bet-selection calls, annual planning, an inherited strategy deck, or a board ask for "our strategy". A strategy kernel: diagnosis, guiding policy, and the actions it implies. Not for sequencing known work (implementation-planning), OKRs (metric-design), or a bounded X-or-Y choice (decision-framing). |
| [requirements-structuring](requirements-structuring/SKILL.md) | Turns a settled intent into requirements a team can build and test from: outcomes, constraints, non-goals, and acceptance criteria a stranger could check. Use when writing or tightening a spec, PRD, ticket, or change request, or when acceptance reads like "works well". Not for deciding whether to build it (decision-framing), diagnosing a slowdown (root-cause-debugging), or planning a rollout (launch-readiness). |
| [research](research/SKILL.md) | Finds out what is true and returns a sourced brief, in one of three modes: look something up or compare options from primary sources; verify a contested claim, number, or timeline against records; or reconstruct why a company did something from tickets, history, docs, and people. Use for "find out", "is this still current", "check whether that's true", "why was this built this way", "who actually owns this". Not for deciding what to do with the facts (decision-framing). |
| [root-cause-debugging](root-cause-debugging/SKILL.md) | Explains a failure before fixing it: reproduce safely, read the whole error, find what changed, test one falsifiable hypothesis at a time by observation, account for the whole symptom, prove the fix both ways. Use for a failing test, an exception, a regression, "works locally", or a metric or funnel that moved for no known reason. Not for a cause the error already names (fix it), or for defining a metric (metric-design). |
| [written-voice](written-voice/SKILL.md) | Rewrites or drafts prose for other people in one plain, direct voice: decision first, no hype, claims only as strong as the evidence, no machine tells. Use for specs, proposals, status updates, announcements, READMEs, and reports, or when asked to make something sound less like a robot wrote it. Not for commit messages (commit-and-pr), chat replies, or what the document should decide. |
